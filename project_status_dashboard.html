Retry and backoff behavior RetryLogicTests
Solves: Whether a transient network blip (a dropped connection, a 5xx from GitHub) gets treated the same as a genuine, non-recoverable failure, a real reliability gap named in GAP_ANALYSIS.md before this was built.
Tests prove: Connection errors and 5xx responses retry with exponential backoff up to 3 attempts and eventually succeed if the underlying condition clears; a 403 rate-limit response and a 404 make exactly one call each, confirmed by test, not assumed from reading the code, since retrying either of those wastes a call and cannot succeed.

Insights: observations, blockers, recommendations

Written to support a decision, not just to describe status.

Observations
  • The independent-verification discipline has now caught ten real, non-hypothetical bugs by running something (six at build time, four in the first hosted days), not zero, and not the same one twice. The first six: the staleness calculation using the wrong branch, MCP error messages being silently sanitized before reaching a caller, a partial API failure mid-pull previously producing a false 'active' status, a race condition in the live test suite's own rate-limit check, a stale SDK field name in the agent's tool-schema conversion, and a list-shaped tool result silently truncated to its first item before ever reaching a model. All six were found by actually running something for real, never by code review alone. The four found in the hosted days were a live test asserting something untrue of the repo it queried, the scheduler reading each repo's first check as a change, a commit-list ETag that changed with no new commit, and a test that deleted the real pull_results.json; see INCIDENT_LOG.md for the full account, and for four further gaps found by reading or reasoning that are not counted.
  • The two newest bugs (incidents #5 and #6) both lived in agent_client.py, the one file that had sat the longest without anything actually exercising it, and both were found within the first hour the new eval harness existed, before any live model was ever involved. That's the clearest evidence yet for why 'written correctly against the documented APIs' and 'verified' are different claims, not a restatement of a principle, an instance of it.
  • 125 of 127 automated tests (98%) pass as of the last run in the build sandbox, up from 73 tests at Phase 9. The remaining 2 are live-network tests that skip without network access there, reported as skipped, not passed, precisely so that distinction stays visible. The hosted runs are reported green on Python 3.10 to 3.12; the skip count in those logs has not been checked here.
  • Phase 9 built four of Tier 5's five named components (alerting, an unattended cron schedule, a live grounding eval distinct from Phase 8's scaffolding eval, and an operational incident-log template) without fabricating the fifth, real users. Of the four, only the unattended schedule has since run for real (just over two days, from 25 Nov 2026). Phase 10, built to the user's own direct correction of the pull cadence ('once every 24 hours unless prompted for more, no more than 3 pulls in a 24 hour window'), replaced the unconditional daily pull with a scheduler enforcing exactly that, and found a second real CI-persistence gap in the process: without committing pulse_run_log.jsonl and etag_cache.json back to the repo between ticks, the whole cadence would have silently collapsed to 'pull every tick.' Hosting then showed the scheduler deciding wrongly twice, on 25 and 26 Nov, each time caught by the owner reading the decision log and not by an alert, which is a gap in the alerting.
  • GitHub access has been the single most recurring operational friction point across this entire build, across two different forms now, the unauthenticated rate limit during the original build, and this build environment's own network policy blocking unauthenticated reads entirely during Phase 8, more consistently than any actual code defect encountered.
  • Every remediation pass so far has surfaced at least one new real defect rather than confirming the code was already correct; Phases 9 and 10 held the pattern in a smaller way first (a dependency-install gap and a state-persistence gap in the CI workflow, both caught by inspection, a lesser category kept out of the count of ten), and hosting then produced four more found by running. The counts are reconciled in INCIDENT_LOG.md and quoted here, not recomputed.
  • This project's own documentation can drift out of sync with itself, not just with reality: MATURITY_ASSESSMENT.md's Tier 5 table had not been updated after Phase 9 shipped alerting, the grounding eval, and the operational-incident template, and still read as if none of them existed. Caught and corrected while adding Phase 10's entries, worth naming as a real process gap, not swept into the Phase 10 changelog as if it were new work.
Blockers
  • This build environment's network policy blocks unauthenticated GitHub reads outright (confirmed by a real attempt during Phase 8, a 403 distinct from a rate-limit exhaustion), on top of GitHub's own unauthenticated rate limit named in earlier phases; both block any fresh live pull against real tracked projects from here.
  • No ANTHROPIC_API_KEY is available in this build environment, so agent_client.py's live model behavior, does it call the right tool, does it ever misstate a figure, remains unverified, and so does grounding_eval.py's model-facing half built in Phase 9. Phase 8 closed the scaffolding-level eval gap around this code; Phase 9 built the grounding-check mechanism on top of it; neither lowers this specific bar, which still needs a live, credentialed run to close.
  • Four things have still never been observed: a scheduled tick performing the baseline pull, a real commit causing an early pull, pulse_alert.py firing against a genuine webhook, and the dashboard as built inside CI. The CI workflow and the scheduler's cap, baseline and state persistence have now been observed in the hosted repo, for just over two days. Scheduled ticks have not landed on the cron slots (00:00, 08:00, 16:00 UTC) and the reason is not established.
Recommendations
  • Set a GITHUB_TOKEN, and confirm this environment's own network policy permits GitHub reads, before the next live demonstration. Two separate blockers now stack on this one point, closing both converts the single most recurring friction point in this build into a non-issue.
  • Run agent_client.py and grounding_eval.py at least once each against a live Anthropic key before describing the agent layer as fully verified or evaluated. This remains the one deliverable in the SOW with a HOLD decision rather than an accept, closing it is a credential away, not a build task.
  • Let the schedule keep running for weeks, not days, and check three things on the way: that a scheduled tick performs the baseline pull, that a real commit on a tracked repo causes an early pull, and that the dashboard built in CI matches the one reviewed. Separately, configure a webhook so pulse_alert.py can deliver, and add an alert condition for a successful run that should not have happened, since both false early pulls so far went unalerted. The hosted repo and the first two OPERATIONAL_INCIDENTS.md entries now exist.
  • Point TRACKED_REPOS at a real engagement and actually use the dashboard operationally, even if the only user at first is the builder. This is the one Tier 5 component (real users) that no further building closes on its own, named explicitly in MATURITY_ASSESSMENT.md rather than left unaddressed.
  • Prioritize the budget point-in-time-vs-burn-rate limitation as the next enhancement. It's the most frequently repeated named gap across METHODOLOGY.md and would most directly strengthen the exact use case, budget decision-making, this system exists to support.
